Capa 4

Cómo se convierte en decisión

Tres consumidores distintos, con papeles que no se solapan.

Los agentes

Seis analistas, cada uno encerrado en su propio material. Responden citando archivo y sección, y si algo no está en su corpus lo dicen en vez de rellenarlo. Están para reproducir el método de cada analista, no para dar una opinión media.

El dashboard

Diecisiete páginas que leen los JSON del almacén. Ninguna recalcula nada por su cuenta — si un número aparece en dos sitios, viene del mismo archivo. El motor de decisión cuenta señales encendidas y propone acción.

Los SOP

El método escrito: gestión de caja, psicología de inversión y las hojas de decisión. Es la capa que convierte una lectura de mercado en una regla que autoriza o prohíbe mover capital.

El circuito completo, en una frase: las fuentes dan el dato, los agentes lo interpretan con el método de su analista, los SOP dicen si eso autoriza una operación, y las hojas la clasifican después para que el track record del mes se pueda contar.
Tu pregunta 5

Los tres sitios donde puedes trabajar

No son intercambiables, y la diferencia no es de potencia sino de acceso.

EntornoQué veQué puede hacerQué NO puede
Chat normal
claude.ai		 Nada del repo Razonar sobre lo que le pegues Leer archivos, ejecutar nada, recordar el estado
Claude Code web
donde hablas conmigo		 Un clon en la nube Leer y escribir código, commitear, lanzar workflows, consultar a los agentes Tocar tu Mac. Y YouTube le bloquea la IP
Claude Code local
la terminal		 Tu carpeta real Todo lo anterior, más ejecutar en tu máquina Nada, dentro del repo

Por qué hace falta el local: hay exactamente tres cosas que no se pueden hacer desde ningún otro sitio.

  1. Los transcripts. YouTube bloquea las IP de datacenter de GitHub con «Sign in to confirm you're not a bot». Desde tu conexión doméstica funciona.
  2. El launchd. El programador vive en tu Mac; nadie puede cargarlo ni comprobarlo desde fuera.
  3. Las wallets fuera del pipeline. Lo que esté en HyperEVM o Hyperliquid solo lo puedes mirar tú.
El reparto que funciona: el local para ejecutar y tocar ficheros; el web para razonar sobre el mercado, interrogar a los agentes y escribir código. Y el chat normal, para esto, no sirve — no ve el repo.
Tu pregunta 6

Cómo se mantienen sincronizados

No hay un mecanismo de sincronización en la aplicación de Claude, y no hace falta: Git ya es exactamente eso. La rama main de GitHub es la única fuente de verdad, y los tres entornos escriben ahí.

Ya automático

ingesta_local.sh hace pull --rebase antes de empezar y push al terminar. Aborta si el árbol está sucio o no estás en main, así que no puede pisar trabajo a medias.

Los workflows

Actions siempre trabaja sobre un clon fresco, así que nunca está desactualizado. Commitea con [skip ci] para no encadenar ejecuciones.

La disciplina que falta

Cuando tú abres una sesión local: git pull antes de nada. Es lo único manual, y es lo que falló dos veces hoy.

Por qué chocan. Hay bots commiteando a main varias veces al día y tú trabajando desde dos sitios. Si empujas sin traer antes, Git rechaza con fetch first — que no es un error, es la protección funcionando. Se arregla siempre igual: git pull --rebase origin main y volver a empujar.

Y si aun así algo se descuadra, hay una red debajo: frescura.py corre todos los días a las 20:00 UTC y compara la fecha de las ocho fuentes contra su límite. Si una se queda atrás —sea por un choque de Git, por un cron muerto o por un motivo que todavía no hemos imaginado— el workflow se pone rojo. No arregla nada; solo se niega a decir que todo va bien.

Este documento describe la estructura, que es estable. Cualquier cifra de mercado caduca en días: para el estado real, python3 ingesta/frescura.py y preguntar a los agentes.
